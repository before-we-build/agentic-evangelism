# Перевірка провайдерів зображень

[English](providers.md) · [Русский](providers.ru.md) · [Українська](providers.uk.md)

## Встановити справжній маршрут доступу

За наявності вбудованого інструмента Codex `image_gen` використовуйте його за замовчуванням. Перевірте справжні інструменти активного середовища. Локальний планувальник обліковує роботу, а середовище викликає інструмент. Команда-кандидат, вхід і успішний вивід довідки самі собою не підтверджують генерації зображень.

На раніше перевіреному телефоні Android/PRoot `agy generate-image --help` повертав загальну довідку. Це спостереження не доводить ані працездатності команди зображень, ані відсутності інструментів зображень у кожній версії AGY. Чинна документація Antigravity описує інструмент генерації зображень і headless-інтерфейс агента з подіями інструментів; перед налаштуванням адаптера перевірте встановлену версію та операцію, яка справді створює файл. [Моделі](https://antigravity.google/docs/models), [headless-інтерфейс](https://antigravity.google/docs/cli/headless/).

Квоти Antigravity залежать від тарифу й обсягу роботи, мають часові вікна та необов'язкові додаткові витрати кредитів. Документована `/usage` (`/quota`) відкриває інтерактивну панель квоти; це не документований універсальний JSON-інтерфейс стану. У наявному термінальному сеансі AGY введіть `/usage`; очікується панель квот. Використовуйте лише підтримуваний адаптер читання або підтверджені користувачем спостереження; не видобувайте облікові дані й не вигадуйте `agy quota --json`. [Тарифи](https://antigravity.google/docs/plans), [панель квоти](https://antigravity.google/docs/cli/commands/usage/).

Генерація зображень Codex використовує загальну квоту підписки; доступ через API-ключ оплачується за правилами API. У наявному термінальному сеансі Codex `/status` показує залишок використання. `python3 scripts/generate.py --probe-codex` за наявності підтримки використовує операції читання облікового запису/стану й прибирає ідентифікатори; вона не дозволяє й не перевіряє генерацію зображень. Відсоток використання не встановлює залишку зображень чи верхньої межі паралельності. [Квоти Codex та оплата зображень](https://learn.chatgpt.com/docs/pricing).

Ліміти API можуть незалежно обмежувати запити, зображення, токени й витрати та бути спільними для моделей, проєкту чи організації. Читайте справжні ліміти облікового запису/моделі та метадані відповідей. Вважайте `Retry-After` мінімальною паузою, відрізняйте тимчасове перевантаження від вичерпаної квоти й обмежуйте повтори. Адаптери мають вимикати приховані автоматичні повтори або явно обліковувати їх. [Ліміти OpenAI API](https://developers.openai.com/api/docs/guides/rate-limits).

Джерела перевірено 2026-09-15; оновлюйте перевірку перед використанням мінливих умов продуктів. Тут немає вбудованих числових лімітів паралельності провайдерів. Pollinations чи інший зовнішній сервіс потребує власної перевіреної операції, чинних доказів доступу/вартості та наданого дозволу; запасна адреса не обирається автоматично.

## Профілі маршрутів і докази

Зберігайте спостереження про обліковий запис, профілі маршрутів і стан планувальника в особистій робочій папці поза репозиторієм. Для `quota_group` використовуйте псевдонім без персональних даних; не зберігайте токени, адреси електронної пошти чи налаштування облікового запису. Формат профілів — `{"schema_version":1,"routes":[...]}`. Кожен маршрут містить:

| Поле | Значення |
| --- | --- |
| `id`, `kind` | Сталий ID; `host_tool`, `cli` або `local`. |
| `quota_group` | Область спільного обліку. Маршрути зі спільною квотою використовують ту саму групу й файл стану. |
| `image_capability`, `entitlement`, `authorized` | Справжня підтримка зображень, право `verified` і дозвіл для завдання. Необхідні значення true/verified мають відображати докази, а не бажаний стан. |
| `subscription` | `{kind: subscription/api/local, plan: ...}`; назва тарифу ніколи не задає місткості. |
| `evidence` | `source`: `host_tool`, `provider_status`, `user_confirmed` або `authorized_smoke_test`; `checked_at` і `expires_at` — секунди Unix. Прострочені докази блокують нові запити. |
| `supports_references` | True лише для маршруту з перевіреною підтримкою референсів. |
| `limits` | `max_parallel`, `initial_parallel`; необов'язкові `requests_per_minute`, `requests_per_day`, `remaining_requests`, `reset_at`. Значення мають означати справжню кількість запитів. |
| `limits.quota_windows` | Необов'язкові спостереження в початкових одиницях: `used_percent`, `window_minutes`, `resets_at`. Вичерпані вікна блокують до отримання свіжих доказів; не переводьте відсотки в кількість зображень. |
| `cost` | `per_request` — перевірена верхня грошова межа за спробу; платні маршрути також потребують `budget_remaining`. У групі квоти використовуйте одну `currency`. Невідома ціна блокує запити. |
| `overage_disabled`, `zero_cost_verified` | Маршрут підписки з нульовою ціною потребує перевіреного `overage_disabled:true`; маршрут API з нульовою ціною — `zero_cost_verified:true`. Включене використання однаково може витрачати квоту. |
| `command`, `timeout_seconds` | Масив аргументів CLI/локального адаптера та час очікування. Команда має реалізувати описаний нижче структурований контракт. |

Якщо одна група квоти охоплює кілька обмежень, використовуйте найсуворіше застосовне спільне обмеження. Планувальник дотримується налаштованих лімітів кількості запитів, паралельності й грошей; він не може вивести витрату токенів/кредитів із тарифу чи гарантувати облік стороннього трафіку поза спільним станом. Оновлюйте спостереження, коли інші сеанси використовують той самий обліковий запис. Відсотки квоти залишаються спостереженнями, а не повною моделлю обліку запитів зі змінною вартістю.

Якщо провайдер не розкриває паралельності, почніть з одного запиту й перед підвищенням `max_parallel` запишіть явно дозволену обмежену межу проби. `initial_parallel` задає обережний початок; успішна робота дозволяє поступове зростання до верхньої межі, обмеження частоти знижує її. Не використовуйте давній успішний запуск як безстроковий доказ. Сам час відновлення не виправдовує поповнення невідомої квоти.

`status_source:"codex_app_server"` підключає маршрут до підтримуваного оновлення стану Codex. Додайте `--refresh-codex-status` до `next`/`run`, щоб оновити дані під час цього запуску. Це не створює автоматичного сервісу опитування, не перевіряє підтримки зображень, не вмикає платних перевитрат і не обходить прострочені докази.

## Планування, резервування, виконання, запис

Запускайте наведені команди з папки цього скіла. На Android використовуйте ту саму оболонку Termux/PRoot, де працюють Python і вибраний генератор. Замініть `/private/...` власними доступними особистими шляхами. Очікуються JSON-плани, резервування та звіти про стан.

```sh
python3 scripts/generate.py --discover
python3 scripts/generate.py --profiles /private/routes.json --plan
python3 scripts/generate.py --storyboard /private/song/storyboard.json --profiles /private/routes.json --state /private/image-shared.sqlite --run-id song --action next
```

`--discover` повідомляє лише про кандидати в PATH; `--plan` перевіряє придатність і невідомі дані без викликів або резервування. `next` резервує придатну роботу до генерації. Усі процеси зі спільною квотою мають використовувати один файл стану, а відновлення того самого розкадрування — той самий ID запуску. Окремі файли стану не координуються між собою.

Об'єкти підтримують `depends_on`, `reference_asset_ids`, `review_required`, `reviewed`, `review_token`, `allowed_routes`, `requires_references` та `affinity_group`. Явно задайте зразок → проба переносу → залежні сцени через `depends_on`; для зразка/проби встановіть `review_required:true`. Використовуйте `reference_asset_ids` для передавання згенерованих зразків у залежні виклики; це також встановлює залежності. Після перегляду зображення встановіть для об'єкта `reviewed:true` і `review_token`, рівний точному `token` із відповіді `record`, та відновіть роботу. Токен прив'язує перевірку до цього файла; старе логічне значення не може підтвердити нове зображення. Утримуйте повторювані образи на сумісному маршруті через `affinity_group`; вимоги до референсів залишаються обов'язковими. Зберігайте надані `characters[].avatar_image` та `assets[].character_ids`.

`limits.remaining_checked_at` і `cost.budget_checked_at` визначають незалежні знімки залишків. Оновлення відсотків квоти не має поновлювати старий грошовий бюджет. `--action status` показує стан планувальника без запуску запитів. `--dry-run` використовує окремий файл стану із суфіксом `.dry-run`. Типово результати зберігаються поряд із розкадруванням, тому його відносні шляхи залишаються чинними; інша вихідна папка потребує перевірки шляхів експортованого розкадрування перед збиранням відео.

Для кожного повернутого резервування запускайте рівно один відповідний виклик вбудованого інструмента з його промптом і необхідними референсами. Збережіть зображення, перегляньте його й запишіть структурований результат в особистий файл, наприклад `{"status":"success","output":"/private/song/images/scene01.png"}`. Потім зареєструйте його з ID роботи й токеном резервування, які повернув `next`:

```sh
python3 scripts/generate.py --storyboard /private/song/storyboard.json --profiles /private/routes.json --state /private/image-shared.sqlite --run-id song --action record --job-id scene01 --token LEASE_TOKEN --result /private/result.json
```

Токен резервування — локальні дані планувальника, не облікові дані API. Записуйте завершення відразу й знову викликайте `next`, поки інші зображення ще генеруються. Не чекайте завершення всієї хвилі перед заповненням вільної місткості. Завжди дочікуйтеся всіх запущених викликів середовища до завершення виконання коду.

Стани результату: `success`, `review_required`, `rate_limited`, `transient_error`, `quota_exhausted`, `unauthorized`, `permanent_error` або `ambiguous`; результати, що допускають повтор, можуть містити `retry_after` у секундах. Перевищений час очікування чи втрачена відповідь можуть означати успішну віддалену роботу. Залишайте неоднозначні завдання для з'ясування результату; не повторюйте їх навмання чи вже завершені об'єкти. Відновлення має зберігати оригінали, а зміни потребують нових шляхів/ID замість перезапису успішного результату.

## Необов'язкові CLI-адаптери

`--action run --allow-external-cli` запускає лише придатні налаштовані CLI/локальні адаптери. Кожна команда отримує JSON через stdin із промптом, `reference_images`, шляхом результату й відомостями про роботу та повертає JSON через stdout за контрактом результатів вище. Загальна відповідь агента CLI сама собою не є зображенням: перевіряйте справжній файл. Адаптери мають враховувати референси, дотримуватися дозволів середовища, зберігати файли й точно повідомляти помилки провайдера. Не реалізуйте текстовий запасний маршрут для сцени, залежної від аватара.

`--dry-run` використовуйте лише для локальних перевірок планувальника; крихітні заглушки не є готовими ілюстраціями. Наданий раніше дозвіл може охоплювати маршрут, але ні прапорці конфігурації, ні копіювання скіла не надають нових прав на сервіс, витрати, публікацію чи видалення.
